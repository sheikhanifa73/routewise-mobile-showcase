Shared architecture

One pattern across Swift, Kotlin, React Native and Flutter.

The language changes; the responsibilities do not. This reduces duplicated business rules and makes bugs easier to isolate.

1. UISwiftUI / UIKit view, Android screen, RN or Flutter widget
2. StateViewModel/controller owns loading, content, error and offline states
3. Use caseBooking, cancellation, check-in and role policy rules
4. RepositoryOne contract for API and local cache
5. API clientAuth, TLS, retries, request IDs, DTO mapping
6. DataModels, cache, sync queue, tests and observability
API & offline

Crash-resistant booking flow

Disable repeated submission while a booking is pending.
Use a server-issued idempotency key for every booking write.
Cache last successful schedule read; display its age.
Queue only safe offline actions; make conflicts visible.
Map network, expired-session and validation errors separately.
Security & privacy

Fitness data deserves product-grade handling.

Keychain/Keystore for short-lived tokens, never user passwords.
TLS and server-side role-based access: consumer, trainer, studio admin.
Tokenized payment provider; never store raw card data.
Minimum permissions for location, health/wellness and notifications.
PII-safe logs and deletion/export flows designed with backend.
Performance & battery

Measure first; optimize the expensive path.

Paginate trainer/session lists; cache images and avoid blocking the main thread.
Use push and targeted background refresh, not constant polling.
Cancel screen-bound requests and debounce search input.
Profile scrolling, memory and launch time with Instruments.
Track crashes, API latency and booking conversion after release.
Clean-code example

Why this boundary prevents crashes and duplicate data.

// Swift: UI never calls URLSession directly. final class BookSessionViewModel: ObservableObject { @Published private(set) var state: LoadState<Booking> = .idle private let repository: SessionRepository func book(sessionID: String) async { guard !state.isLoading else { return } // avoids double tap state = .loading do { let key = UUID().uuidString state = .content(try await repository.book(sessionID, idempotencyKey: key)) } catch let error as SessionError { state = .error(error.userMessage) // typed, recoverable UI state } catch { state = .error("Please try again.") } } } // Repository decides API vs cache and centralizes mapping/retry policy.
Lead delivery plan

How I would turn Figma and requirements into a shippable feature.

1. Define the contract

Acceptance criteria, roles, edge cases, API payload, failure states, analytics and release flag before coding.

2. Build vertical slices

Ship one end-to-end session booking flow through UI, repository, API contract and tests rather than isolated screens.

3. Release with proof

Unit/UI tests, test-flight/internal Android testing, crash monitoring, staged rollout and measurable rollback criteria.
